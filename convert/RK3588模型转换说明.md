# RK3588 YOLOv8 模型转换示例

本文演示如何使用 `convert/` 中的脚本和 Docker 环境，将 Ultralytics YOLOv8
检测模型转换为可在 RK3588 上部署的 RKNN 模型。

本文是通用示例，不包含特定项目的数据集、类别、模型文件或验收结论。
文中的 `best.pt`、`class_a`、`class_b` 和 `example.jpg` 均为占位名称，
使用时请替换为自己的文件。

## 1. 适用范围

本示例适用于：

- Ultralytics YOLOv8 Detect 检测模型。
- 单输入、三通道图片模型。
- 需要导出 slim-head，即原始回归和分类输出的场景。
- 目标平台为 RK3588，且转换工具与板端 RKNN runtime 版本匹配的环境。

默认示例使用 RKNN Toolkit2 1.5.0。其他 Toolkit2、Ultralytics 或模型版本
可能需要调整依赖和导出代码，不能直接套用输出形状或后处理逻辑。

## 2. 目录说明

```text
convert/
├── docker/                 # Dockerfile、Compose 和环境配置
├── python/                 # 导出、校准、转换和验证脚本
├── scripts/                # Shell 入口
└── work/                   # 本地工作区，不提交数据和生成物
    ├── best.pt             # 示例权重，可替换
    ├── dataset/            # INT8 校准图片
    │   ├── class_a/
    │   ├── class_b/
    │   └── ...
    └── output/             # ONNX、RKNN 和 JSON 清单
```

`work/` 只用于存放本地文件。除说明文件外，其内容不进入 Git 和 Docker
构建上下文，容器通过挂载方式读取输入并写入输出。

## 3. 环境要求

转换在 PC 上执行，不是在 RK3588 板卡上执行。

| 项目 | 示例配置 |
|---|---|
| 主机架构 | x86_64 |
| 容器系统 | Ubuntu 22.04 |
| Python | 3.10 |
| PyTorch / torchvision | 2.4.0 / 0.19.0，CPU 版本 |
| Ultralytics | 8.1.0 |
| ONNX | 1.13.1，opset 12 |
| ONNX Runtime | 1.14.1 |
| RKNN Toolkit2 | 1.5.0 |
| 目标平台 | `rk3588` |

需要提前安装 Docker Engine 和 Docker Compose。首次构建需要联网，不需要
NVIDIA GPU。

Toolkit2、板端 `librknnrt.so` 和 NPU 驱动需要兼容。部署前应检查设备实际
环境，不能只依据模型能否在 PC 上生成来判断板端是否可运行。

## 4. 准备输入

默认读取以下文件：

```text
work/
├── best.pt
└── dataset/
    ├── class_a/
    │   ├── image001.jpg
    │   └── ...
    └── class_b/
        ├── image001.jpg
        └── ...
```

权重必须是当前导出脚本支持的 YOLOv8 checkpoint。

INT8 量化需要准备有代表性的校准图片。`dataset/` 下的一级子目录用于按类
均衡抽样，目录名只是校准分组标识，不会自动成为模型的类别名称。

模型类别名称和顺序应读取 checkpoint 的 `names` 元数据，不要根据校准目录
名称或目录排序推断。

FP16 转换不执行 INT8 校准，因此不需要校准图片。

## 5. 构建并使用转换环境

以下命令从仓库根目录开始执行。环境构建和模型转换是两个独立步骤：
先确认镜像可用，再根据自己的权重和数据执行转换。

### 5.1 创建本地配置

进入 Docker 配置目录，并从示例创建 `.env`：

```bash
cd convert/docker
cp .env.example .env
```

Windows PowerShell 也可以使用：

```powershell
Copy-Item .env.example .env
```

`.env` 用于保存本机路径和转换参数，不需要提交到 Git。

### 5.2 构建转换镜像

```bash
docker compose build converter
```

如果使用的是旧版 Compose：

```bash
docker-compose build converter
```

首次构建需要联网下载依赖，后续构建会复用 Docker 缓存。默认镜像名为
`rknn-convert:1.5.0-slim`，可通过 `.env` 中的 `IMAGE_NAME` 修改。

该步骤只构建环境，不需要准备权重，也不会执行模型转换。

### 5.3 验证转换环境

```bash
docker compose run --rm --entrypoint python3 converter -c "import torch, onnx, onnxruntime, ultralytics; from rknn.api import RKNN; print('RKNN conversion environment OK')"
```

旧版 Compose 同样只需将 `docker compose` 换成 `docker-compose`。

看到以下输出即表示关键依赖可以正常加载：

```text
RKNN conversion environment OK
```

### 5.4 执行模型转换

按照第 4 节准备好 `work/best.pt` 和 `work/dataset/` 后运行：

```bash
docker compose run --rm converter
```

旧版 Compose 使用：

```bash
docker-compose run --rm converter
```

如果修改了 Dockerfile、Python 依赖或转换脚本，可以在转换时同时重新构建：

```bash
docker compose run --rm --build converter
```

转换完成后，临时容器自动删除，ONNX、RKNN 和 JSON 清单保留在
`work/output/`。

## 6. 转换流程

完整流程由 `scripts/run_convert.sh` 串联：

```text
YOLOv8 checkpoint
    |
    v
export_onnx.py
    |
    v
slim ONNX
    |
    +--> prepare_quant_dataset.py  # 仅 INT8
    |         |
    |         v
    |       dataset.txt + calibration.json
    |
    v
to_rknn.py
    |
    v
RKNN model + rknn.json
```

各步骤职责如下：

| 脚本 | 作用 |
|---|---|
| `python/export_onnx.py` | 加载 checkpoint、替换 Detect 头、导出并检查 ONNX |
| `python/prepare_quant_dataset.py` | 按目录均衡抽取校准图片，记录路径和 SHA-256 |
| `python/to_rknn.py` | 配置目标平台和量化参数，构建并导出 RKNN |
| `scripts/run_convert.sh` | 串联完整转换流程 |
| `scripts/entrypoint.sh` | Docker 容器入口 |

## 7. slim-head 输出

标准 YOLOv8 Detect 头通常包含 DFL、anchor 生成、坐标还原和分类 sigmoid。
slim-head 导出保留回归与分类分支的原始输出，将这些后处理移到 CPU。

| 对比项 | 融合 Detect 头 | slim-head |
|---|---|---|
| 回归输出 | 已解码的框 | 原始 DFL 分布 |
| 分类输出 | 可能已经过 sigmoid | 原始 logits |
| DFL / anchor | 模型图内执行 | CPU 执行 |
| 部署后处理 | 阈值与 NMS | sigmoid、DFL、anchor、NMS 和坐标反变换 |

设：

- 输入尺寸为 `S x S`。
- 类别数为 `C`。
- `reg_max=16`，回归通道数为 `4 x 16 = 64`。
- 三档 stride 为 `8、16、32`。
- anchor 总数为 `N`。

则：

```text
input      : [1, 3, S, S]
output_reg : [1, 64, N]
output_cls : [1, C, N]

N = (S / 8)^2 + (S / 16)^2 + (S / 32)^2
```

例如 `S=640` 且模型使用上述三档 stride 时，`N=8400`。此时分类输出为
`[1,C,8400]`，其中 `C` 由实际模型决定。

这些形状仅适用于对应的 YOLOv8 Detect 结构。自定义检测头、不同 stride 或
其他模型系列需要重新计算。

## 8. CPU 后处理要求

使用 slim RKNN 模型时，部署端需要完成以下步骤：

1. 根据输出名称、形状和布局读取 `output_reg` 与 `output_cls`。
2. 对分类 logits 执行 sigmoid。
3. 按置信度筛选候选 anchor。
4. 对回归分布执行 DFL，得到 `left/top/right/bottom` 四组距离。
5. 根据 anchor 位置和对应 stride 还原输入坐标系中的检测框。
6. 执行 class-aware NMS。
7. 根据预处理时的缩放比例和 padding，将框还原到原图坐标。

DFL 的距离计算为：

```text
p_k = softmax(reg[i*16 + k])
d_i = sum(k * p_k), k = 0..15
```

其中 `i=0,1,2,3` 分别对应四条边。距离还需要与对应 anchor 的 stride 一起
参与坐标还原，不能直接当作原图像素值。

后处理必须与模型导出实现保持一致，尤其要检查：

- anchor 的 level 顺序和网格遍历顺序。
- 网格中心偏移量。
- DFL 通道排列。
- NCHW 与 NHWC 内存布局。
- letterbox 缩放比例和左右、上下 padding。

## 9. INT8 与 FP16

| 模式 | 校准图片 | 特点 | 常见用途 |
|---|---|---|---|
| INT8 | 需要 | 模型较小，通常速度更快，但需要评估量化误差 | 正式部署候选 |
| FP16 | 不需要 | 便于建立较高精度对照，模型通常更大 | 精度和兼容性对照 |

Toolkit2 1.5.0 没有名为 `fp16` 的 `quantized_dtype`。本示例的 `FP16`
选项在 1.x 工具链中映射为 `asymmetric_quantized-16`，实际使用的 dtype 会
记录在输出 JSON 清单中。

校准图片应覆盖模型实际使用场景，不应只选择容易识别的样本。最终精度需要在
独立验证集上评估，不能用校准集结果代替。

## 10. 常用配置

编辑 `docker/.env` 修改转换参数：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `WEIGHTS_DIR` | `../work` | 权重所在目录 |
| `WEIGHTS_FILE` | `best.pt` | 权重文件名 |
| `CALIB_DIR` | `../work/dataset` | 校准图片目录 |
| `CALIB_NUM` | `200` | 校准图片总数 |
| `OUTPUT_DIR` | `../work/output` | 输出目录 |
| `PLATFORM` | `rk3588` | RKNN 目标平台 |
| `INPUT_SIZE` | `640` | 正方形输入边长 |
| `QUANTIZED` | `INT8` | `INT8` 或 `FP16` |
| `HEAD_MODE` | `slim` | `slim` 或 `fused` |
| `OPTIMIZATION_LEVEL` | `3` | RKNN 图优化级别 `1/2/3` |
| `OPSET` | `12` | ONNX opset |
| `SEED` | `42` | 校准抽样随机种子 |

`CALIB_NUM` 默认在一级类别目录之间均分，因此必须能被类别目录数整除。
需要显式指定每类数量时，可直接调用转换入口并使用 `--per-class N`。

优化级别越高并不代表在所有模型和设备上都更好。需要对照时，可分别生成
不同优化级别的模型，并使用相同输入和后处理参数比较。

## 11. 输出文件

以 `best.pt`、slim、INT8、优化级别 3 为例：

```text
work/output/
├── best_slim.onnx
├── best_slim.onnx.json
├── best_slim_dataset.txt
├── best_slim_calibration.json
├── best_slim_int8_opt3.rknn
└── best_slim_int8_opt3.rknn.json
```

更换权重文件名、量化方式或优化级别后，输出文件名会相应变化。

RKNN 的 JSON 清单记录源 ONNX、校准清单、目标平台、量化类型、优化级别、
Toolkit2 版本和 SHA-256。建议将清单与模型一起保存，便于追溯和核对。

相同配置的重复转换会覆盖同名输出。需要保留历史结果时，请修改
`OUTPUT_DIR`。

## 12. PC 侧验证示例

以下命令演示如何对照 Ultralytics 与参考解码器。请先将示例图片路径替换为
实际存在的文件：

```bash
cd convert/docker
docker compose run --rm --entrypoint python3 converter \
  /opt/convert/verify_slim.py \
    --weights /input/best.pt \
    --onnx /out/best_slim.onnx \
    --image /calib/class_a/example.jpg \
    --output /out/verify_slim.json
```

验证报告可用于检查 anchor、分类分数和最终检测框是否对齐。

PC 侧数值验证不能替代 RK3588 真机验证，也不能单独证明量化后的业务精度。

## 13. 板端验证建议

部署到 RK3588 后，至少检查：

- `rknn_init` 和 `rknn_run` 是否成功。
- 实际输入输出名称、形状、类型和布局是否与清单一致。
- CPU 后处理结果是否与 PC 参考结果一致。
- 独立验证集上的类别、置信度和检测框是否满足要求。
- 连续运行时是否出现超时、内存增长或 NPU 异常。
- 预处理、推理、后处理和端到端耗时是否满足需求。

如果模型不能加载或执行，应优先检查 Toolkit2、runtime、NPU 驱动和目标
平台的兼容性，再排查模型图和后处理。

## 14. 常见问题

| 现象 | 检查方向 |
|---|---|
| 找不到 `best.pt` | 检查 `WEIGHTS_DIR`、`WEIGHTS_FILE` 和挂载路径 |
| 校准目录为空或不存在 | 检查 `CALIB_DIR`；FP16 不需要该校准目录 |
| 校准数量无法均分 | 调整 `CALIB_NUM`，或使用 `--per-class` |
| checkpoint 无法导出 slim-head | 确认模型是兼容的 YOLOv8 Detect 结构 |
| 输出形状与示例不同 | 检查输入尺寸、stride、类别数和检测头结构 |
| `Invalid quantized_dtype 'fp16'` | 检查 Toolkit2 版本及 16bit 映射是否生效 |
| 容器入口出现 CRLF 错误 | 将 Shell 脚本转换为 LF；Dockerfile 也提供兼容处理 |
| 模型在 PC 生成成功但板端失败 | 核对 Toolkit2、runtime、驱动、平台和优化级别 |

## 15. 示例边界

本文只说明通用转换方法，不附带可识别特定项目的数据、权重或检测结果。
任何示例文件名、目录名和参数都需要根据实际模型与设备确认。

转换成功只表示模型文件已生成，不代表目标设备上的精度、稳定性和性能已经
通过验收。
