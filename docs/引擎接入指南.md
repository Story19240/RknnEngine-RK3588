# RknnEngine 接入指南

## 1. 概述与分工边界

RknnEngine 是面向 RK3588 Android 设备的通用 RKNN 推理引擎。客户端向引擎提交一帧
`Bitmap`，引擎从应用 `assets` 加载 RKNN 模型，完成输入转换与预处理、NPU 推理，
并通过回调返回模型输入信息和各阶段耗时。通用模型返回全部输出张量；YOLOv8
slim-head 模型还可在 native 层完成后处理并返回结构化检测框。

引擎当前只处理通用推理链路，不包含相机、图形界面或任何具体业务算法。职责边界如下：

| 范围 | 引擎负责 | 客户负责 |
|---|---|---|
| 模型 | 从 `assets` 读取模型文件并初始化 RKNN runtime | 提供合法的 `.rknn` 模型并确认模型转换参数 |
| 输入 | 接收 `Bitmap`；必要时转为 `ARGB_8888`，再转换为三通道 RGB | 采集帧、选择送入引擎的帧、完成方向校正和裁剪策略 |
| 预处理 | 按模型输入尺寸等比缩放，居中填充到固定尺寸 | 如业务另有要求，在提交前完成客户侧预处理 |
| 推理 | 调用 RKNN runtime 在 NPU 上执行模型 | 保证模型、运行时和设备兼容 |
| 输出 | 返回模型名、帧尺寸、输入尺寸、耗时、输出张量和可选检测结果 | 消费通用张量或结构化检测结果 |
| 生命周期 | 创建 native 上下文、加载模型、同步执行推理、释放资源 | 管理实例、关闭时机、线程调度和异常恢复 |

调用关系如下：

```text
客户帧采集
    |
    v
Bitmap
    |
    v
RknnEngine.submitFrame(...)
    |
    +--> RknnWrapper：预处理 -> RKNN runtime -> 输出处理
    |
    v
EngineCallback.onResult(...) / EngineCallback.onError(...)
    |
    v
客户侧消费原始张量或结构化检测结果
```

调用 `loadModel(assetManager, modelName)` 时使用通用透传后处理；调用带
`DetectionConfig` 的重载时，native 层识别 `output_reg`/`output_cls` 并完成
sigmoid、DFL、anchor 还原、NMS 和原图坐标反变换。

当前 Java API 以同步调用方式提交帧：`submitFrame` 返回时，本次推理已经完成，结果或错误已通过 `EngineCallback` 回调送达。引擎不会自行创建帧队列，也不会切换线程；客户应在后台线程调用，并在需要时将回调结果转交主线程。

## 2. 交付物与模块引入

### 2.1 文件与模块对照

| 交付内容 | 仓库路径 | 作用 |
|---|---|---|
| Android AAR 模块 | `android/rknn-engine/` | 可供客户应用依赖的 Android library module |
| Java API | `android/rknn-engine/src/main/java/com/rknn/engine/` | `RknnEngine` 门面、回调接口、结果对象和输出张量对象 |
| JNI 实现 | `android/rknn-engine/src/main/cpp/jni/rknn_engine_jni.cpp` | Java 与 native 之间的对象转换、Bitmap 读取和回调调用 |
| 通用封装 | `android/rknn-engine/src/main/cpp/rknn/rknn_wrapper.{h,cpp}` | RKNN 模型加载、输入输出查询、预处理、推理和计时 |
| YOLOv8 后处理 | `android/rknn-engine/src/main/cpp/rknn/rknn_yolov8_output_processor.{h,cpp}` | slim reg/cls 布局识别、DFL、anchor、NMS 和坐标反变换 |
| Host 回归测试 | `android/rknn-engine/src/test/cpp/` | 不依赖 Android SDK 的 native 解码测试 |
| RKNN runtime | `android/rknn-engine/src/main/cpp/third_party/rknn/arm64-v8a/librknnrt.so` | 随 AAR 打包的 arm64-v8a RKNN runtime 1.5.0 |
| RKNN API 头文件 | `android/rknn-engine/src/main/cpp/third_party/rknn/rknn_api.h` | native 编译所用 RKNN 1.5.0 API 声明 |
| OpenCV Mobile | `android/rknn-engine/src/main/cpp/third_party/opencv-mobile-4.10.0-android/` | Bitmap 转换、缩放和填充使用的 arm64-v8a 静态库与头文件 |
| Native 库 | `librknnengine.so` | 构建产物，由 CMake 的 `rknnengine` target 生成 |

### 2.2 工程引入

若客户应用与本仓库处于同一 Gradle 工程，在应用的根 `settings.gradle` 中包含模块：

```gradle
include ':rknn-engine'
```

在客户应用模块的 `build.gradle` 中依赖 AAR 模块：

```gradle
dependencies {
    implementation project(':rknn-engine')
}
```

客户也可以取得构建产物后以 AAR 方式引入。无论采用哪种方式，都应确认以下信息：

| 项 | 当前值 | 来源或约束 |
|---|---|---|
| Gradle 模块名 | `rknn-engine` | `android/settings.gradle` |
| Java 包名 / namespace | `com.rknn.engine` | `android/rknn-engine/build.gradle` |
| Java API 导入 | `import com.rknn.engine.*;` | 公开 Java 类均位于 `com.rknn.engine` |
| 支持 ABI | 仅 `arm64-v8a` | Gradle `abiFilters` 与 CMake 检查均限定该 ABI |
| Native 库加载名 | `rknnengine` | `RknnEngine` 内部调用 `System.loadLibrary("rknnengine")` |

客户应用需具备设备 `arm64-v8a` 的 native 库加载能力。模块启用了 `useLegacyPackaging = true`，使随包 native 库进入 AAR 的传统 `jni/<abi>/` 目录。

### 2.3 构建命令

在本仓库的 Android 工程根目录执行：

```bash
cd android
./gradlew :rknn-engine:assembleDebug
```

构建完成后，AAR 位于 `android/rknn-engine/build/outputs/aar/`。正式交付时可使用 `assembleRelease` 生成 release AAR；当前模块的 release 构建未启用代码压缩，也未配置发布签名。

构建环境应满足第 3 章列出的 JDK、Gradle、AGP、SDK、NDK 和 CMake 版本要求。
完成 AAR 构建后，还应在目标 RK3588 设备上验证 `librknnrt.so` 加载、模型初始化和
连续推理，不能以主机编译成功代替设备验证。

### 3.3 模型兼容要求

客户提供的模型应满足以下要求：

- 使用 RKNN Toolkit2 `1.5.0` 转换。
- 转换目标设置为 `rk3588`。
- 只有一个三通道输入，且输入为 4 维张量；当前实现只接受单输入、RGB 三通道模型。
- 模型应包含至少一个输出张量。
- 输入尺寸由模型自身定义，引擎在加载时查询并据此建立输入缓冲。

模型代际或目标平台不匹配时，RKNN runtime 会在模型初始化阶段返回错误。客户应在接入前核对转换日志和模型来源，避免使用其他目标平台或更高 Toolkit2 代际生成的模型。

## 4. 模型文件

### 4.1 assets 放置

当前引擎模块在 `android/rknn-engine/src/main/assets/` 中附带两个 INT8 slim
示例模型：`yolov8n.rknn` 对应 opt=3，`yolov8n_opt1.rknn` 对应 opt=1。
实际项目应使用自己的模型并完成目标设备验证。模型可放入客户应用的
`assets` 目录，例如：

```text
app/
└── src/main/assets/
    ├── yolov8n.rknn
    └── yolov8n_opt1.rknn
```

文件名可由客户自行决定。传给 `loadModel` 的名称必须是相对于 `assets` 根目录的
资源名，例如 `yolov8n.rknn`、`yolov8n_opt1.rknn` 或 `models/model.rknn`；
当前实现直接使用该字符串打开 asset，不接受绝对文件系统路径。

### 4.2 加载方式

从客户应用取得 `AssetManager`，再调用 `RknnEngine.loadModel`：

```java
AssetManager assets = getApplicationContext().getAssets();
boolean loaded = engine.loadModel(assets, "yolov8n.rknn");
```

加载过程由 native 层完成：

1. 通过 `AAssetManager_open` 打开 asset。
2. 读取完整文件内容和长度。
3. 将模型字节复制到 native 内存。
4. 调用 `rknn_init` 初始化模型上下文。
5. 查询输入、输出数量以及张量属性。
6. 为全部输出预分配 `float` 缓冲，并按模型输入尺寸创建输入缓冲。

`loadModel` 返回 `true` 表示模型已成功加载；返回 `false` 表示参数无效、asset 不存在或 RKNN 初始化失败。模型加载失败不会触发 `EngineCallback.onError`，客户应在调用点处理返回值。

同一个引擎实例再次调用 `loadModel` 时，旧模型上下文会先被释放，再加载新模型。若新模型加载失败，实例中不会保留旧模型。客户应避免在推理过程中切换模型。

## 5. API 参考

本章覆盖 `com.rknn.engine` 下公开类的实例方法和公开构造方法。示例中的 `engine`
均指 `RknnEngine` 实例。

### 5.1 RknnEngine

源码：[`RknnEngine.java`](../android/rknn-engine/src/main/java/com/rknn/engine/RknnEngine.java)

#### 构造方法

```java
public RknnEngine()
```

- **参数**：无。
- **返回值**：无。
- **行为**：加载 `librknnengine.so`，创建 native 引擎句柄。
- **异常**：native 句柄创建失败时抛出 `IllegalStateException`。
- **线程约束**：构造期间不要从其他线程访问该实例。创建实例本身不需要 Android 主线程。

#### `loadModel`

```java
public synchronized boolean loadModel(AssetManager assetManager, String modelName)

public synchronized boolean loadModel(
        AssetManager assetManager,
        String modelName,
        DetectionConfig detectionConfig)
```

- **参数**：
  - `assetManager`：非空 `AssetManager`，通常取自 `Context.getAssets()`。
  - `modelName`：非空 asset 相对路径，例如 `yolov8n.rknn`。
  - `detectionConfig`：可选。传入时启用 YOLOv8 slim-head native 解码；传入
    `null` 时与两参数重载等价。
- **返回值**：模型加载成功返回 `true`；句柄已释放、参数无效、文件不存在或 native 加载失败返回 `false`。
- **回调**：失败时不调用 `EngineCallback.onError`。
- **线程约束**：方法为同步方法，同一实例上的 `loadModel`、`submitFrame` 和 `close` 不会并发进入。加载期间不应提交推理任务。
- **注意**：成功加载会替换该实例此前加载的模型。

缺陷模型示例：

```java
boolean loaded = engine.loadModel(
        assets,
        "yolov8n.rknn",
        DetectionConfig.forDefectModel());
```

切换到 opt=1 备选时只需把资源名改为 `"yolov8n_opt1.rknn"`，检测阈值、NMS
参数和类别映射保持不变，才能进行可比的 A/B 测试。

`DetectionConfig.forDefectModel()` 使用固定类别索引：
`0变形 / 1涂层丢失 / 2烧灼烧穿 / 3缺损 / 4裂纹`。

#### `setResultCallback`

```java
public void setResultCallback(EngineCallback callback)
```

- **参数**：`callback` 为结果回调；传入 `null` 可清除回调。
- **返回值**：无。
- **行为**：保存当前回调引用。回调字段为 `volatile`，可在其他线程更新。
- **线程约束**：本方法本身不加实例锁，可在任意线程调用。应在首次提交帧前设置。
- **注意**：未设置回调时，`submitFrame` 直接返回 `false`，不会执行推理。

#### `submitFrame`

```java
public synchronized boolean submitFrame(Bitmap frame)
```

- **参数**：`frame` 为待推理帧，不能为 `null`，也不能已经回收。
- **返回值**：native 推理流程返回 0 时为 `true`；参数无效、未设置回调、Bitmap 转换失败或推理失败时为 `false`。
- **回调**：
  - 推理成功时调用一次 `EngineCallback.onResult`。
  - Bitmap 转换失败或 native 推理失败时调用一次 `EngineCallback.onError`。
- **线程约束**：方法为同步方法，同一实例上的 `loadModel`、`submitFrame` 和 `close` 串行执行。回调在调用 `submitFrame` 的线程同步执行，因此应在后台线程调用，避免阻塞主线程。

#### `close`

```java
public synchronized void close()
```

- **参数**：无。
- **返回值**：无。
- **行为**：释放 native 句柄、RKNN 上下文和关联缓冲。重复调用是安全的。
- **线程约束**：同步方法；会等待同一实例上正在执行的 `submitFrame` 或 `loadModel` 结束。销毁页面或业务模块时调用，并在调用后释放对实例的其他引用。
- **注意**：关闭后再次调用 `loadModel` 或 `submitFrame` 均返回 `false`。

#### 公开错误常量

| 常量 | 值 | 含义 |
|---|---:|---|
| `RknnEngine.ERROR_INVALID_ARGUMENT` | `-1` | 参数无效或 Bitmap 无法转换 |
| `RknnEngine.ERROR_ENGINE_UNAVAILABLE` | `-2` | 模型尚未加载或引擎不可用 |
| `RknnEngine.ERROR_INFERENCE_FAILED` | `-3` | RKNN 推理流程失败 |
| `RknnEngine.ERROR_CALLBACK_FAILED` | `-4` | native 结果对象创建失败 |
| `RknnEngine.ERROR_MODEL_LOAD_FAILED` | `-5` | 模型资产不存在或模型不可用 |

### 5.2 EngineCallback

源码：[`EngineCallback.java`](../android/rknn-engine/src/main/java/com/rknn/engine/EngineCallback.java)

```java
public interface EngineCallback {
    void onResult(InferenceResult result);
    void onError(EngineError error);
}
```

| 方法 | 参数 | 返回值 | 线程约束 |
|---|---|---|---|
| `onResult` | `InferenceResult result`：本次推理的模型、尺寸、耗时和输出张量 | 无 | 由 `submitFrame` 的调用线程同步触发 |
| `onError` | `EngineError error`：错误码、消息和可用的帧尺寸 | 无 | 由 `submitFrame` 的调用线程同步触发 |

回调内应快速完成必要工作并及时返回。需要在界面线程更新状态时，将结果投递到客户自己的主线程 handler。

### 5.3 EngineError

源码：[`EngineError.java`](../android/rknn-engine/src/main/java/com/rknn/engine/EngineError.java)

#### 构造方法

```java
public EngineError(int code, String message, int frameWidth, int frameHeight)
```

- **参数**：
  - `code`：错误码，见第 10 章。
  - `message`：错误说明。
  - `frameWidth`：错误发生时的源帧宽度；无法取得时可为 0。
  - `frameHeight`：错误发生时的源帧高度；无法取得时可为 0。
- **返回值**：无。
- **线程约束**：可由客户在任意线程构造；引擎在回调中传入的对象由调用线程接收。

| `int getFrameWidth()` | 源帧宽度 | 部分 native 错误无法取得尺寸时为 0 |
| `int getFrameHeight()` | 源帧高度 | 部分 native 错误无法取得尺寸时为 0 |

### 5.4 InferenceResult

源码：[`InferenceResult.java`](../android/rknn-engine/src/main/java/com/rknn/engine/InferenceResult.java)

#### 构造方法

```java
public InferenceResult(
```

- **线程约束**：该对象由 `EngineCallback.onResult` 传入，读取操作可放在任意线程。

#### 读取方法

| 方法 | 返回值 | 说明 |
|---|---|---|
| `String getModelName()` | 模型名 | 当前值为传给 `loadModel` 的 asset 名 |
| `int getFrameWidth()` | 源帧宽度 | 进入引擎的 Bitmap 宽度 |
| `int getFrameHeight()` | 源帧高度 | 进入引擎的 Bitmap 高度 |
| `int getInputWidth()` | 模型输入宽度 | 从模型输入属性查询得到 |
| `int getInputHeight()` | 模型输入高度 | 从模型输入属性查询得到 |
| `double getPreprocessMillis()` | 毫秒数 | `RknnWrapper` 内 letterbox 缩放与填充耗时 |
| `double getInferenceMillis()` | 毫秒数 | `rknn_run` 耗时 |
| `double getPostprocessMillis()` | 毫秒数 | 读取输出、执行输出处理并释放 native 输出缓冲的耗时 |
| `double getTotalMillis()` | 毫秒数 | 从预处理开始到输出处理完成的累计耗时 |
| `TensorOutput[] getOutputs()` | 输出数组 | 按 RKNN 输出顺序排列；无输出时不会成功完成本次推理 |
| `DetectionResult getDetectionResult()` | 检测结果 | 通用模型为空集合；检测模型包含最终检测框 |

- **返回值**：无。
- **线程约束**：该对象由 `EngineCallback.onResult` 传入，读取操作可放在任意线程。

#### 读取方法

| 方法 | 返回值 | 说明 |
|---|---|---|
| `String getName()` | 张量名 | 来自 RKNN 输出属性；具体名称由模型决定 |
| `int[] getShape()` | 维度数组 | 维度顺序来自 RKNN 输出属性 |
| `float[] getValues()` | 数据数组 | 已按行优先连续排列，元素数量为各维度之积 |
| `String getFormat()` | 布局字符串 | `NCHW`、`NHWC`、`UNDEFINED` 或 `UNKNOWN` |

当前 Java API 不单独提供张量 `index`、数据类型、量化类型、零点或缩放系数。调用方
可用 `InferenceResult.getOutputs()` 中的数组位置标识输出顺序；具体量化解释方式
应以模型转换配置和 RKNN runtime 行为为准。

### 5.6 DetectionConfig

源码：[`DetectionConfig.java`](../android/rknn-engine/src/main/java/com/rknn/engine/DetectionConfig.java)

检测模式配置，包含置信度阈值、NMS IoU 阈值、最大检测数、是否透传 raw 输出和
类别名称表。`forDefectModel()` 提供本项目 5 类缺陷模型的默认配置。

```java
public DetectionConfig(
        float confidenceThreshold,
        float nmsThreshold,
        int maxDetections,
        String[] classNames)

public DetectionConfig(
        float confidenceThreshold,
        float nmsThreshold,
        int maxDetections,
        boolean includeRawOutputs,
        String[] classNames)
```

阈值必须位于 `[0,1]`，`maxDetections` 必须为正数，否则构造时抛出
`IllegalArgumentException`。`includeRawOutputs` 默认为 `false`。

### 5.7 Detection

源码：[`Detection.java`](../android/rknn-engine/src/main/java/com/rknn/engine/Detection.java)

单个不可变检测结果，提供 `getClassId()`、`getClassName()`、`getConfidence()`、
`getLeft()`、`getTop()`、`getRight()` 和 `getBottom()`。坐标已经反变换到源图，
单位为像素，顺序为 `x1,y1,x2,y2`，并裁剪在源图边界内。

### 5.8 DetectionResult

源码：[`DetectionResult.java`](../android/rknn-engine/src/main/java/com/rknn/engine/DetectionResult.java)

检测结果集合，提供 `getDetections()`、`size()` 和 `isEmpty()`。`getDetections()`
返回数组副本，调用方不能通过它修改内部集合。

## 6. 输入规范

### 6.1 Bitmap 要求

送入引擎的 `Bitmap` 应满足：

- 非 `null`，且没有调用 `recycle()`。
- 宽、高均大于 0。
- 内容方向已由客户校正；引擎不会读取或修正相机方向。
- 在调用期间保持有效，直到 `submitFrame` 返回。

Java 层会把非 `ARGB_8888` 的 Bitmap 复制为 `ARGB_8888`。native 层按 Android `RGBA_8888` 布局读取像素，再通过 OpenCV 转为三通道 RGB。若复制失败，引擎调用 `onError`，错误码为 `ERROR_INVALID_ARGUMENT`。

### 6.2 引擎内部预处理

当前固定预处理流程如下：

1. 将 Bitmap 的 RGBA 像素转换为连续的三通道 RGB。
2. 从模型输入属性读取目标宽、高和通道数；当前只接受三通道单输入模型。
3. 计算等比缩放系数：

   ```text
   scale = min(inputWidth / sourceWidth, inputHeight / sourceHeight)
   ```

4. 按该系数线性插值缩放，缩放后宽高至少为 1，且不超过模型输入尺寸。
5. 在目标画布四周居中填充，左右和上下留白由整数除法计算。
6. 以 RGB 值 `114` 填充留白区域。
7. 将连续 RGB `uint8` 数据以 `NHWC` 格式交给 RKNN runtime，输入 `pass_through=0`。

引擎不会在 Java 层执行均值、标准差或通道顺序归一化，也不会读取客户提供的预处理参数；模型相关的输入转换由 RKNN runtime 按模型属性处理。

### 6.3 客户侧职责

使用默认 letterbox 预处理时，客户无需再次缩放、补边或转换像素格式。客户仍需负责：

- 选择要送入模型的帧。
- 根据设备方向和传感器方向旋转或镜像画面。
- 如业务需要，在送入引擎前完成裁剪、ROI 选择或颜色空间调整。
- 保证送入内容与模型训练时的方向语义一致。

通用结果对象只公开源帧尺寸和模型输入尺寸，不公开缩放系数与填充偏移。检测模式
已在 native 层使用这些内部参数完成坐标反变换，客户直接读取 `Detection` 即可；
通用模型若需要自行还原有效区域，应结合源帧与输入尺寸计算。

## 7. 输出规范

### 7.1 InferenceResult

一次成功推理对应一个 `InferenceResult` 对象，字段含义如下：

| 字段 | 类型 | 来源与含义 |
|---|---|---|
| `modelName` | `String` | `loadModel` 传入的 asset 名 |
| `frameWidth` | `int` | 进入引擎的源 Bitmap 宽度 |
| `frameHeight` | `int` | 进入引擎的源 Bitmap 高度 |
| `inputWidth` | `int` | 模型输入张量宽度 |
| `inputHeight` | `int` | 模型输入张量高度 |
| `preprocessMillis` | `double` | `RknnWrapper` 内 letterbox 缩放与填充耗时 |
| `inferenceMillis` | `double` | `rknn_run` 耗时 |
| `postprocessMillis` | `double` | 读取输出、执行输出处理并释放 native 输出缓冲的耗时 |
| `totalMillis` | `double` | native 推理流程总耗时 |
| `outputs` | `TensorOutput[]` | 通用模式的全部输出张量；检测模式默认可能为空 |
| `detectionResult` | `DetectionResult` | 结构化检测结果；通用模式为空集合 |

四个耗时字段单位均为毫秒。`totalMillis` 包含 letterbox 预处理、`rknn_run` 和 native 输出读取 / 释放，但不等同于 Java 层从调用 `submitFrame` 到收到回调的全部时间；其中不包含 Bitmap 格式转换复制、RGBA 转 RGB、Java 结果对象构造、跨线程调度和客户侧回调后处理。

### 7.2 TensorOutput

每个 `TensorOutput` 对应模型的一个 RKNN 输出张量：

| 字段 | 类型 | 当前公开语义 |
|---|---|---|
| 输出顺序 | `InferenceResult.getOutputs()` 数组下标 | 与 RKNN 输出顺序一致，可作为当前 Java API 下的输出标识 |
| `name` | `String` | 模型中的输出名称 |
| `shape` | `int[]` | RKNN 输出属性中的维度列表 |
| `values` | `float[]` | 按行优先排列的连续浮点数据 |
| `format` | `String` | RKNN 输出布局，如 `NCHW` 或 `NHWC` |

数据读取方式：

```java
TensorOutput[] outputs = result.getOutputs();
for (int outputIndex = 0; outputIndex < outputs.length; outputIndex++) {
    TensorOutput output = outputs[outputIndex];
    int[] shape = output.getShape();
    float[] values = output.getValues();

    int elementCount = 1;
    for (int dimension : shape) {
        elementCount *= dimension;
    }

    // values.length 应与 elementCount 一致；values 按行优先顺序索引。
    float firstValue = values.length > 0 ? values[0] : 0.0f;
    Log.d("RknnEngine",
            "output=" + outputIndex
                    + ", name=" + output.getName()
                    + ", shape=" + shape.length
                    + ", values=" + values.length
                    + ", first=" + firstValue);
}
```

读取多维张量的某个元素时，可按行优先规则计算线性下标：

```text
offset = (((index0 * dimension1 + index1) * dimension2 + index2) ...)
```

当前实现通过 `want_float=1` 请求 RKNN runtime 输出浮点值，并使用预分配的 `float` 缓冲承接数据。因此 Java 层拿到的是运行时转换后的 `float[]`，不是模型文件中的原始量化字节。

当前 Java `TensorOutput` 没有公开以下 native 元数据：

- RKNN 输出张量属性中的 `index` 数值。
- 张量数据类型 `type`。
- 量化类型 `qnt_type`。
- 零点 `zp`。
- 缩放系数 `scale`。

这些信息存在于 `RknnTensorInfo`，但当前 JNI 转换只把 `name`、`shape`、
`values` 和 `format` 传给 Java。客户若依赖其余元数据，应以模型转换配置为准；
不得从 `float[]` 反推唯一的原始量化参数。

### 7.3 输出数组约定

- 通用模式的输出数组包含模型的全部输出，不只包含客户关心的一个张量。
- 数组顺序与 `rknn_outputs_get` 使用的输出顺序一致。
- 当前成功推理要求模型至少有一个输出。
- `values` 数组和 `shape` 数组由本次结果独立创建；引擎完成推理后不会继续修改这些 Java 数组。
- 客户应避免在主线程遍历很大的输出数组；可在后台线程完成数据消费后再把摘要送到主线程。
- 检测模式的 `includeRawOutputs` 默认为 `false`，此时 `getOutputs()` 返回空数组，
  避免为 slim 模型每帧复制约 2.32 MB 的 raw float。

### 7.4 结构化检测结果

检测模式从 `result.getDetectionResult().getDetections()` 读取结果。每个框的坐标
已经从模型输入空间反变换到源 Bitmap，顺序为 `left,top,right,bottom`，单位为
像素；置信度范围为 `[0,1]`。空集合表示本帧没有达到阈值的检测。

```java
for (Detection detection : result.getDetectionResult().getDetections()) {
    Log.d(TAG,
            detection.getClassId()
                    + ":" + detection.getClassName()
                    + " score=" + detection.getConfidence()
                    + " box=" + detection.getLeft()
                    + "," + detection.getTop()
                    + "," + detection.getRight()
                    + "," + detection.getBottom());
}
```

## 8. 接入示例

以下代码均属于客户应用侧示例，引擎模块本身不包含相机和界面代码。

### 8.1 最小接入

下面的示例展示完整调用顺序：创建引擎、加载模型、提交一帧、读取输出并释放资源。

```java
import android.content.res.AssetManager;
import android.graphics.Bitmap;
import android.util.Log;

import com.rknn.engine.EngineCallback;
import com.rknn.engine.EngineError;
import com.rknn.engine.InferenceResult;
import com.rknn.engine.RknnEngine;
import com.rknn.engine.TensorOutput;

public final class MinimalRknnClient {
    private static final String TAG = "MinimalRknnClient";
    private final RknnEngine engine;

    public MinimalRknnClient() {
        engine = new RknnEngine();
    }

    public boolean start(AssetManager assets, String modelName) {
        engine.setResultCallback(new EngineCallback() {
            @Override
            public void onResult(InferenceResult result) {
                TensorOutput[] outputs = result.getOutputs();
                for (TensorOutput output : outputs) {
                    Log.d(TAG, "output=" + output.getName()
                            + ", shapeLength=" + output.getShape().length
                            + ", valueCount=" + output.getValues().length);
                }
            }

            @Override
            public void onError(EngineError error) {
                Log.e(TAG, "inference failed: code=" + error.getCode()
                        + ", message=" + error.getMessage());
            }
        });

        boolean loaded = engine.loadModel(assets, modelName);
        if (!loaded) {
            Log.e(TAG, "model load failed: " + modelName);
        }
        return loaded;
    }

    public boolean infer(Bitmap frame) {
        // submitFrame 是同步调用；返回时回调已经执行。
        return engine.submitFrame(frame);
    }

    public void stop() {
        engine.close();
    }
}
```

调用顺序要求：

1. 创建 `RknnEngine`。
2. 设置 `EngineCallback`。
3. 调用 `loadModel` 并检查返回值。
4. 持有有效 Bitmap，调用 `submitFrame`。
5. 在 `onResult` 中读取输出，或在同步调用返回后通过客户自己的状态容器读取最近结果。
6. 不再使用实例时调用 `close`。

最小示例直接在调用线程接收回调。生产应用通常应按下一节把推理放入后台单线程。

缺陷模型只需把加载调用改为：

```java
boolean loaded = engine.loadModel(
        assets,
        modelName,
        DetectionConfig.forDefectModel());
```

随后从 `result.getDetectionResult()` 读取检测框，不再遍历 raw reg/cls 张量。

### 8.2 推荐管理类封装

下面的客户侧管理类使用一个后台单线程执行模型加载和同步推理。任一时刻最多保留一个待处理帧，忙时新到帧被丢弃；native 回调先到达后台线程，再切换到主线程交付给客户。

```java
import android.content.res.AssetManager;
import android.graphics.Bitmap;
import android.os.Handler;
import android.os.Looper;
import android.util.Log;

import com.rknn.engine.EngineCallback;
import com.rknn.engine.EngineError;
import com.rknn.engine.InferenceResult;
import com.rknn.engine.RknnEngine;

import java.io.Closeable;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicBoolean;

public final class RknnEngineManager implements EngineCallback, Closeable {
    private static final String TAG = "RknnEngineManager";

    public interface Listener {
        void onResult(InferenceResult result);
        void onError(EngineError error);
        void onLoadError(String message);
    }

    private final ExecutorService worker = Executors.newSingleThreadExecutor();
    private final Handler mainHandler = new Handler(Looper.getMainLooper());
    private final AtomicBoolean framePending = new AtomicBoolean(false);
    private final AtomicBoolean ready = new AtomicBoolean(false);
    private final AtomicBoolean closed = new AtomicBoolean(false);
    private final Listener listener;

    private RknnEngine engine;

    public RknnEngineManager(Listener listener) {
        this.listener = listener;
    }

    public void start(AssetManager assets, String modelName) {
        worker.execute(() -> {
            try {
                if (closed.get()) {
                    return;
                }

                RknnEngine created = new RknnEngine();
                created.setResultCallback(this);
                if (!created.loadModel(assets, modelName)) {
                    created.close();
                    postLoadError("Failed to load model: " + modelName);
                    return;
                }

                engine = created;
                ready.set(true);
            } catch (RuntimeException exception) {
                postLoadError("Failed to create engine: " + exception.getMessage());
            }
        });
    }

    /**
     * 复制一份 ARGB_8888 Bitmap 交给后台线程。
     * 方法接管副本，推理结束后由 worker 回收；调用方仍拥有并负责原 Bitmap。
     */
    public boolean submitFrame(Bitmap frame) {
        if (frame == null || frame.isRecycled() || closed.get() || !ready.get()) {
            return false;
        }

        if (!framePending.compareAndSet(false, true)) {
            return false; // 上一帧仍在处理，丢弃当前帧。
        }

        final Bitmap ownedFrame;
        try {
            ownedFrame = frame.copy(Bitmap.Config.ARGB_8888, false);
        } catch (RuntimeException | OutOfMemoryError exception) {
            framePending.set(false);
            return false;
        }

        if (ownedFrame == null) {
            framePending.set(false);
            return false;
        }

        worker.execute(() -> {
            try {
                RknnEngine current = engine;
                if (!closed.get() && current != null) {
                    current.submitFrame(ownedFrame);
                }
            } finally {
                ownedFrame.recycle();
                framePending.set(false);
            }
        });
        return true;
    }

    @Override
    public void onResult(InferenceResult result) {
        mainHandler.post(() -> {
            if (!closed.get()) {
                listener.onResult(result);
            }
        });
    }

    @Override
    public void onError(EngineError error) {
        mainHandler.post(() -> {
            if (!closed.get()) {
                listener.onError(error);
            }
        });
    }

    @Override
    public void close() {
        if (!closed.compareAndSet(false, true)) {
            return;
        }

        ready.set(false);
        worker.execute(() -> {
            RknnEngine current = engine;
            engine = null;
            if (current != null) {
                current.close();
            }
        });
        worker.shutdown();
    }

    private void postLoadError(String message) {
        Log.e(TAG, message);
        mainHandler.post(() -> {
            if (!closed.get()) {
                listener.onLoadError(message);
            }
        });
    }
}
```

该封装采用以下策略：

- **后台单线程**：所有 native 操作串行执行，符合引擎实例的同步调用模型。
- **丢帧保护**：用原子标记限制待处理帧数量；上一帧未完成时，新帧直接返回 `false`。
- **主线程回调**：`onResult` 和 `onError` 从 worker 线程切换到主线程后交付给客户。
- **关闭时机**：`close` 先阻止新帧和回调，再在 worker 队列末尾释放引擎，最后关闭 executor。
- **Bitmap 生命周期**：管理类复制并接管副本，原 Bitmap 始终由调用方管理。

客户可根据帧率和内存预算调整复制与丢帧策略。如果客户已经在后台线程持有独占 Bitmap，也可以改为由管理类接管该 Bitmap，并在推理结束后回收。

### 8.3 帧来源

#### 已有 Bitmap 回调

客户已有 Bitmap 回调时，可直接提交：

```java
bitmapCallback.onBitmapAvailable(bitmap -> {
    if (!bitmap.isRecycled()) {
        engineManager.submitFrame(bitmap);
    }
});
```

同步直调引擎时，Bitmap 至少要保持到 `submitFrame` 返回：

```java
boolean accepted = engine.submitFrame(bitmap);
// submitFrame 返回后再释放由客户拥有的 bitmap。
```

#### ImageProxy 转 Bitmap

CameraX `ImageProxy` 的可用转换方式取决于所用 CameraX 版本和图像格式。较新版本可直接调用 `ImageProxy.toBitmap()`：

```java
import android.graphics.Bitmap;
import androidx.camera.core.ImageProxy;

private Bitmap imageProxyToBitmap(ImageProxy image) {
    if (image.getFormat() == android.graphics.ImageFormat.JPEG) {
        java.nio.ByteBuffer buffer = image.getPlanes()[0].getBuffer();
        byte[] bytes = new byte[buffer.remaining()];
        buffer.get(bytes);
        return android.graphics.BitmapFactory.decodeByteArray(bytes, 0, bytes.length);
    }

    // 要求客户所用 CameraX 版本提供 ImageProxy.toBitmap()。
    return image.toBitmap();
}
```

若客户所用 CameraX 版本没有 `ImageProxy.toBitmap()`，应使用客户已经验证的 YUV/RGBA 转 Bitmap 工具。无论采用哪种方式，都应在 `ImageProxy.close()` 前完成 Bitmap 转换；使用第 8.2 节的管理类时，复制后的副本可由管理类在后台推理结束后回收。

#### 方向校正

引擎不读取 `ImageProxy.imageInfo.rotationDegrees`，也不会自动旋转 Bitmap。客户应在提交前按 `rotationDegrees` 校正方向：

```java
import android.graphics.Bitmap;
import android.graphics.Matrix;

private Bitmap rotate(Bitmap source, int rotationDegrees) {
    if (rotationDegrees == 0) {
        return source;
    }

    Matrix matrix = new Matrix();
    matrix.postRotate((float) rotationDegrees);
    return Bitmap.createBitmap(
            source,
            0,
            0,
            source.getWidth(),
            source.getHeight(),
            matrix,
            true);
}
```

客户应确认镜头的旋转与镜像语义，使送入引擎的方向和模型训练数据一致。完成方向校正后，不再需要为引擎额外做 letterbox。

## 9. 生命周期与线程模型

### 9.1 实例生命周期

推荐的实例状态顺序：

```text
new RknnEngine()
    -> setResultCallback(...)
    -> loadModel(...)
    -> submitFrame(...) 可重复调用
    -> close()
```

- `new RknnEngine()` 创建 native 上下文，但此时没有模型。
- `loadModel` 成功后才能提交推理。
- 一个实例当前只承载一个已加载模型；再次加载会替换旧模型。
- `close` 释放 native 资源，之后实例不可复用。
- 多个实例可以分别持有模型，但每个实例都会创建自己的 RKNN 上下文和缓冲。客户应按实际吞吐需求控制实例数量。

### 9.2 调用线程

| 操作 | 线程要求 |
|---|---|
| 构造 `RknnEngine` | 任意线程；不要与其他线程并发访问尚未发布的新实例 |
| `loadModel` | 可在任意线程调用；与同一实例的提交和关闭串行 |
| `setResultCallback` | 任意线程；字段为 `volatile` |
| `submitFrame` | 建议在专用后台线程调用；会同步等待推理完成 |
| `EngineCallback.onResult` | 与 `submitFrame` 同一线程同步触发 |
| `EngineCallback.onError` | 与 `submitFrame` 同一线程同步触发 |
| `close` | 可在任意线程调用；会等待同一实例的同步操作完成 |

`submitFrame`、`loadModel` 和 `close` 都以实例级同步方法串行化。native 层还对单个句柄使用 mutex，因此不会在同一个实例上并发执行模型操作。

### 9.3 回调约束

- 回调不是异步任务；`submitFrame` 返回前已经调用完结果或错误回调。
- 回调执行期间，Java 实例的同步方法锁仍处于持有状态。回调内不要执行耗时的数据处理。
- 不建议从回调中再次调用同一实例的 `loadModel` 或 `close`。需要切换模型或释放实例时，由外层控制线程在当前回调结束后执行。
- 回调抛出的 Java 异常会在 JNI 边界被清理，不会反向传播为 `submitFrame` 的 Java 异常；客户仍应在回调内部自行记录异常。

### 9.4 关闭与资源回收

- `close` 可重复调用。
- 关闭前应停止向引擎提交新帧。
- 使用后台队列时，应先停止生产新帧，再让队列中的当前任务结束，最后释放 native 实例。
- 客户拥有的 Bitmap、CameraX `ImageProxy`、相机线程和界面对象不由引擎关闭；这些资源由客户按其生命周期管理。
- native 句柄释放时，RKNN 上下文、模型字节副本、输入缓冲和输出缓冲一并释放。

### 9.5 模型加载失败

`loadModel` 的失败只通过 `false` 返回，不会触发 `EngineCallback.onError`。客户应在启动流程中单独处理加载失败，避免后续持续提交帧。推荐管理类示例通过 `onLoadError` 将这类失败转交客户。

## 10. 错误码与排障

### 10.1 三种错误口径

当前接口存在三条不同的错误表达路径，不能只看一个数字判断原因。

#### 路径一：Java 方法的布尔返回值

| 方法 | 返回 `false` 的已知条件 | 是否同时触发 `onError` |
|---|---|---|
| `loadModel` | 实例已关闭、`assetManager` 为 `null`、模型名为 `null` 或空串；asset 无法打开；asset 缓冲为空；RKNN 模型初始化或模型结构检查失败 | 否 |
| `submitFrame` | 实例已关闭、Bitmap 为 `null` 或已回收、尚未设置回调、Bitmap 转换失败、native 推理失败 | 仅 Bitmap 转换失败和 native 推理失败会触发 |

`loadModel` 当前只向 Java 返回 `true` / `false`。native 层的具体返回值以及 RKNN runtime 的原始错误码都会在 Java 边界被折叠为 `false`，模型加载失败时不会产生 `EngineError`。

#### 路径二：EngineError 中的错误码

`EngineError.getCode()` 保存 JNI 层传入的数值。引擎定义了以下 Java 错误常量：

| Java 常量 | 数值 | 当前触发场景 |
|---|---:|---|
| `ERROR_INVALID_ARGUMENT` | `-1` | Bitmap 无法转换为 `ARGB_8888`；native 读取到的 Bitmap 格式或尺寸无效；像素锁定失败 |
| `ERROR_ENGINE_UNAVAILABLE` | `-2` | 提交帧时模型尚未加载，或 native 句柄不可用 |
| `ERROR_INFERENCE_FAILED` | `-3` | native 推理流程的通用失败初值 |
| `ERROR_CALLBACK_FAILED` | `-4` | native 推理成功，但构造 Java 结果对象失败 |
| `ERROR_MODEL_LOAD_FAILED` | `-5` | native 层的模型资产不可用常量；当前模型加载路径不会把它包装为 `EngineError` |

需要注意：推理过程中 `RknnWrapper::infer` 返回的 RKNN runtime 原始负值会原样进入 `EngineError.getCode()`。这些原始值与上表数值存在重合，例如 `-2` 在 Java 常量中表示引擎不可用，在 RKNN API 中则表示超时。因此仅看到 `-2` 时，必须结合 `getMessage()`、错误发生阶段和模型加载结果判断，不能脱离上下文套用错误表。

#### 路径三：native / RKNN 原始错误码

`rknn_api.h` 定义了以下 runtime 错误：

| 原始码 | RKNN 名称 | 含义 |
|---:|---|---|
| `0` | `RKNN_SUCC` | 执行成功 |
| `-1` | `RKNN_ERR_FAIL` | 执行失败 |
| `-2` | `RKNN_ERR_TIMEOUT` | 执行超时 |
| `-3` | `RKNN_ERR_DEVICE_UNAVAILABLE` | 设备不可用 |
| `-4` | `RKNN_ERR_MALLOC_FAIL` | 内存分配失败 |
| `-5` | `RKNN_ERR_PARAM_INVALID` | 参数无效 |
| `-6` | `RKNN_ERR_MODEL_INVALID` | 模型无效 |
| `-7` | `RKNN_ERR_CTX_INVALID` | 上下文无效 |
| `-8` | `RKNN_ERR_INPUT_INVALID` | 输入无效 |
| `-9` | `RKNN_ERR_OUTPUT_INVALID` | 输出无效 |
| `-10` | `RKNN_ERR_DEVICE_UNMATCH` | 设备不匹配，需要更新 RKNN SDK |
| `-11` | `RKNN_ERR_INCOMPATIBLE_PRE_COMPILE_MODEL` | 预编译模型与当前驱动不兼容 |
| `-12` | `RKNN_ERR_INCOMPATIBLE_OPTIMIZATION_LEVEL_VERSION` | 优化级别与当前驱动版本不兼容 |
| `-13` | `RKNN_ERR_TARGET_PLATFORM_UNMATCH` | 模型目标平台与当前平台不匹配 |

当前 Java 模型加载 API 不暴露这些原始码。推理阶段的原始码可能通过 `EngineError.getCode()` 到达客户；排查模型加载失败时，应结合 RKNN 转换日志、模型目标平台和设备环境判断，不能只依赖 `loadModel` 的布尔值。

### 10.2 常见问题

| 现象 | 代码层行为 | 检查方向 |
|---|---|---|
| 尚未加载模型就提交帧 | `submitFrame` 返回 `false`；`onError` 收到 `ERROR_ENGINE_UNAVAILABLE`（`-2`） | 等待 `loadModel` 成功后再开放帧提交 |
| 没有设置回调就提交帧 | `submitFrame` 返回 `false`；不触发 `onError` | 在首次提交前调用 `setResultCallback` |
| Bitmap 为 `null`、已回收或实例已关闭 | `submitFrame` 返回 `false`；不触发 `onError` | 检查帧所有权、回收时机和实例状态 |
| Bitmap 格式转换失败 | `onError` 收到 `ERROR_INVALID_ARGUMENT`（`-1`），消息为 `Failed to convert frame to ARGB_8888` | 使用可复制为 `ARGB_8888` 的 Bitmap；避免不可复制或内存不足的帧 |
| native 无法按 `RGBA_8888` 读取 Bitmap | `onError` 收到 `-1`，消息为 `Frame must be a non-empty RGBA_8888 bitmap` | 确认传入的是有效 `ARGB_8888` Bitmap，宽高非零 |
| 模型 asset 名称错误 | `loadModel` 返回 `false`；无 `onError` | 核对相对 `assets` 根目录的名称和大小写 |
| 模型 asset 无法提供连续缓冲 | `loadModel` 返回 `false`；无 `onError` | 确保模型以可缓冲读取的资源打包；当前实现通过 `AAsset_getBuffer` 读取模型内容 |
| 模型代际或目标平台不匹配 | `rknn_init` 返回 runtime 错误，`loadModel` 将其折叠为 `false` | 使用 RKNN Toolkit2 1.5.0 转换，并设置 `target_platform=rk3588` |
| 模型输入或输出结构不受支持 | `loadModel` 返回 `false`；无 `onError` | 模型必须恰有一个三通道输入，并至少有一个输出 |
| 推理阶段收到 RKNN 原始负值 | `EngineError.getCode()` 可能直接是 runtime 原始码 | 按第 10.1 节第三张表核对，并检查驱动、模型和输入 |
| 应用安装后无法加载 native 库 | Java 类初始化时可能抛出 `UnsatisfiedLinkError` | 确认设备为 `arm64-v8a`，且 AAR 中包含 `librknnengine.so` 与 `librknnrt.so` |
| 回调耗时拖慢采集 | `submitFrame` 同步等待，回调也在同一调用线程执行 | 在后台线程调用引擎，并把客户侧结果处理移到合适线程 |

### 10.3 排障信息采集

建议客户在问题反馈中保留以下信息：

- `RknnEngine.submitFrame` 的布尔返回值。
- `EngineError.getCode()`、`getMessage()`、帧宽高。
- 模型名、模型文件 md5、转换工具版本和 `target_platform`。
- 设备型号、Android 版本 / API level、板端 NPU 驱动版本。
- `InferenceResult` 中的源帧尺寸、模型输入尺寸和三段耗时。
- 是否能稳定复现，以及问题发生在首次加载、首次推理还是连续运行阶段。

当前引擎不会自行打印模型加载或推理错误日志，也不会把 `loadModel` 的 native 原始错误详情传回 Java。客户应在调用点记录 `loadModel` 的结果，并结合模型转换记录定位。

## 11. 性能与常见坑

### 11.1 执行模型

当前引擎是单模型、单帧、同步执行模型：

- 每次 `submitFrame` 只处理一帧，不做批处理。
- native 层不维护待处理帧队列，也不自行丢帧。
- 同一实例的模型操作由 Java 同步方法和 native mutex 串行化。
- 推理使用 `rknn_init` 的默认 NPU core 策略，当前 Java API 不暴露分核配置。
- 输入以 `UINT8`、`NHWC`、`pass_through=0` 提交，由 RKNN runtime 按模型输入属性完成输入转换。
- 输出全部以 `want_float=1` 读取，native 层使用预分配 `float` 缓冲承接结果。

客户应把引擎调用放在专用后台线程，并根据实际帧率设置输入节流。当前引擎不会替客户控制调用频率；连续高频调用会占满该后台线程。

### 11.2 计时边界

四个耗时字段均来自 `RknnWrapper::infer` 内的 `steady_clock`：

| 计时字段 | 起点 | 终点 | 包含 | 不包含 |
|---|---|---|---|---|
| `preprocessMillis` | 调用 `RknnPreprocessor::preprocess` 前 | 预处理返回后 | 等比缩放、居中补边、填充值写入 | Java Bitmap 复制、RGBA 转 RGB |
| `inferenceMillis` | 调用 `rknn_run` 前 | `rknn_run` 返回后 | NPU 推理调用 | 输入提交、输出读取 |
| `postprocessMillis` | 调用 `rknn_outputs_get` 前 | `rknn_outputs_release` 后 | 输出读取、透传或检测后处理、输出释放 | Java 结果对象和数组构造 |
| `totalMillis` | native 预处理开始前 | native 输出释放后 | 上述三段 native 工作 | 模型加载、Java 层前后处理、回调投递和客户消费耗时 |

因此，`totalMillis` 不是端到端业务延迟。客户测得的总延迟还应包含：

- Java 层将非 `ARGB_8888` Bitmap 复制为 `ARGB_8888` 的时间。
- JNI 层将 RGBA 像素转换为 RGB 的时间。
- native 输出复制到 Java `float[]`、创建 `TensorOutput` 和 `InferenceResult` 的时间。
- 线程排队、回调切换到主线程和客户结果处理时间。

### 11.3 数据转换与内存开销

每次成功推理都会产生以下数据复制或分配：

1. 非 `ARGB_8888` 输入在 Java 层复制一份 `ARGB_8888` Bitmap。
2. JNI 层从 Bitmap 读取 RGBA 像素并转换为连续 RGB `cv::Mat`。
3. letterbox 预处理写入按模型尺寸预分配的连续 RGB 输入缓冲。
4. RKNN runtime 将全部输出写入预分配的 native `float` 缓冲。
5. 通用模式由 JNI 为每个输出创建 Java `int[] shape` 和 `float[] values`；检测
   模式默认跳过这一步，只传最终检测框。
6. 回调返回后，由 Java 垃圾回收器处理不再被客户持有的 Bitmap 副本和结果数组。

通用模式的输出数组体积与模型输出元素总数成正比。YOLOv8 slim 模型有 579,600
个 raw float，检测模式默认不再创建对应 Java 数组。客户若使用通用模式处理大
输出模型，应先评估 Java 堆占用，再决定帧率与实例数量。

### 11.4 常见坑

#### 把 `submitFrame` 当作异步接口

`submitFrame` 会同步完成推理并执行回调。它返回 `true` 表示 native 推理流程成功，不只是表示任务已入队。直接在主线程调用会阻塞界面。

#### 在回调中执行耗时工作

回调运行在调用 `submitFrame` 的线程，并处于 Java 实例同步方法的锁范围内。回调内进行大数组遍历、磁盘写入或复杂计算，会直接拉长下一次调用前的等待时间。

#### 误判 `false` 的含义

- `loadModel == false` 只说明加载失败，当前接口不提供具体原因。
- `submitFrame == false` 可能是未加载模型、未设置回调、输入无效，也可能是 native 推理失败。
- native 推理失败时通常还会收到 `onError`；输入为 `null`、已回收、未设置回调等 Java 前置检查失败时不会收到 `onError`。

客户应同时检查布尔返回值和回调，不能只依赖其中一个。

#### 重复做 letterbox

引擎已经按模型尺寸完成等比缩放和居中补边。客户不应在提交前再次做同样的 letterbox，否则会改变模型实际看到的有效区域和留白比例。

#### 忽略方向校正

引擎不会读取相机传感器方向，也不会自动旋转图像。方向错误会让模型收到与训练数据不同的画面。客户应在提交前按设备方向校正。

#### 误用量化输出元数据

当前 Java `TensorOutput` 只提供名称、形状和 `float[]` 数据，不提供输出 `index`、类型、量化类型、零点或缩放系数。数组下标可用于当前结果内定位输出，但不能替代模型的量化定义。

#### 在实例关闭后继续提交

`close` 后 `loadModel` 和 `submitFrame` 都返回 `false`。客户应先停止帧生产，再关闭实例，并避免让后台队列持有已关闭实例。

#### 加载多个模型时并发提交

同一实例再次调用 `loadModel` 会先释放旧模型。客户应停止提交帧并等待当前推理结束后再切换模型。

#### 忽略实例和队列的关闭顺序

后台管理类应在停止生产新帧后，关闭提交入口，等待队列中的当前任务结束，再释放 native 实例并关闭线程池。直接终止线程可能在 native 推理期间销毁引擎资源。

### 11.5 性能验证建议

客户在目标 RK3588 设备上联调时，建议分别记录：

- 相机到 `submitFrame` 的帧间隔。
- `preprocessMillis`、`inferenceMillis`、`postprocessMillis` 和 `totalMillis` 的平均值、P50、P95 与 P99。
- `submitFrame` 从调用到返回的端到端 native 等待时间。
- 回调线程切换和客户侧结果消费时间。
- 稳定运行时的 Java 堆占用、系统内存和 NPU 负载。

性能数字必须来自客户实际模型、输入尺寸、输出规模和 RK3588 设备。引擎仓库中的静态源码检查不能替代目标设备上的吞吐、延迟和稳定性验证。

### 12.5 验证建议

接入变更应按以下层次验证：

1. 执行 native host test，检查 NCHW/NHWC、输出换序、stride、NMS 和异常输出。
2. 使用第 3 章要求的工具链完成 Android AAR 构建，确认目标 ABI 的 native 库齐全。
3. 在目标 RK3588 设备上完成 `rknn_init`、`rknn_run`、输出一致性和重复加载验证。
4. 使用实际模型和图片检查检测精度、边界坐标、连续运行稳定性和分段耗时。

主机测试和 AAR 构建只能证明部分接入链路，不能替代目标设备上的功能、精度和
性能验证。
